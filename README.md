# Мини-CRM «Объекты и задачи»

Небольшая CRM для строительной компании: постановщик ставит задачи по объектам (стройкам), исполнитель берёт их в работу и отправляет на проверку, постановщик принимает или возвращает на доработку. Каждая смена статуса сохраняется в истории.

**Стек:** React + TypeScript (Vite), Supabase (Postgres, Auth, RLS).

## Как запустить

### 1. База данных (Supabase)

1. Создайте проект на [supabase.com](https://supabase.com) (бесплатного тарифа достаточно).
2. Отключите открытую регистрацию: Authentication → Sign In / Providers → Email → выключите **Allow new users to sign up**.
3. Примените миграции из `supabase/migrations/` по порядку (по именам файлов):
   - через SQL Editor: вставьте и выполните каждый файл по очереди;
   - или через CLI: `supabase link --project-ref <ref>` и `supabase db push`.
4. Создайте пользователей вручную: Authentication → Users → Add user (с галочкой Auto Confirm). Для демо нужны:
   `manager1@example.com`, `manager2@example.com`, `executor1@example.com`, `executor2@example.com`.
   Пароли задайте свои.
5. Выполните `supabase/seed.sql` в SQL Editor **один раз целиком**. Он создаёт профили с ролями, 3 объекта и 7 задач в разных статусах с историей.

### 2. Фронтенд

```bash
npm install
cp .env.example .env     # заполните значения
npm run dev
```

Переменные в `.env` (Supabase → Project Settings → API):

| Переменная | Что это |
|---|---|
| `VITE_SUPABASE_URL` | URL проекта |
| `VITE_SUPABASE_ANON_KEY` | публичный ключ (anon / publishable) |

Ключ `service_role` в проекте не используется и в репозиторий попадать не должен.

### 3. Деплой

Подходит Vercel или Netlify: подключите репозиторий, задайте те же две переменные окружения, команда сборки `npm run build`, папка `dist`. Для Vercel в репозитории есть `vercel.json` (перенаправление путей на `index.html`).

## Роли

| Роль | Что может |
|---|---|
| Постановщик | создаёт, редактирует и удаляет объекты и задачи, назначает исполнителя, принимает задачи или возвращает на доработку, видит всё |
| Исполнитель | видит только свои задачи и объекты, где у него есть задачи, берёт задачу в работу и отправляет на проверку |

Переходы статусов: Новая → В работе → На проверке → Принята или На доработке (с обязательным комментарием) → В работе. Остальные переходы запрещены.

## Как защищены данные

Все правила работают на уровне базы, а не только в интерфейсе, поэтому действуют и при прямых запросах к API Supabase:

- включён RLS на всех таблицах, лишние права у ролей `anon` и `authenticated` отозваны;
- исполнитель не читает и не меняет чужие задачи;
- статус задачи нельзя записать напрямую: он меняется только функцией `change_task_status`, которая проверяет переход, роль и комментарий;
- история статусов дополняется только этой функцией, изменить или удалить запись нельзя;
- роль пользователя хранится в таблице `profiles`, изменить её через API нельзя;
- открытая регистрация отключена.

## Структура

```
supabase/migrations/   схема, права (RLS), функция смены статусов
supabase/seed.sql      демо-данные
src/lib/               клиент Supabase, типы, вспомогательный код
src/components/        формы и общие элементы
src/pages/             экраны: вход, объекты, объект, задача, мои задачи
```
