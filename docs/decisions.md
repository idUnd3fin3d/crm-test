# Решения и допущения

## Что я решил сам там, где ТЗ неоднозначно

**Задачи и статусы**

1. **Исполнитель в задаче обязателен.** Иначе задачу в статусе «Новая» никто не сможет взять в работу.
2. **Исполнителем может быть только пользователь с ролью «исполнитель».** Проверяет база, а не только выпадающий список в интерфейсе.
3. **Исполнителя можно менять только в статусах «Новая» и «На доработке».** Пока задача в работе или на проверке, подменить исполнителя нельзя.
4. **Принятая задача заморожена:** её нельзя редактировать.
5. **Постановщик не меняет статус «за исполнителя».** Он может только принять задачу или вернуть на доработку из статуса «На проверке», как в таблице переходов в ТЗ.
6. **Комментарий** – одно необязательное поле на любой переход. Обязателен только при возврате на доработку. Комментарий из одних пробелов считается пустым.
7. **В истории есть первая запись «Создана»** (без исходного статуса), чтобы было видно, кто и когда создал задачу.

**Доступ**

8. **Все постановщики равноправны.** Каждый видит и меняет всё, включая задачи, созданные коллегой. Автор не получает особых прав.
9. **Исполнитель видит в карточке объекта только свои задачи**, а не все задачи объекта. Объекты без его задач он не видит вовсе.
10. **Имена пользователей видят все авторизованные** (нужны, чтобы показать автора и исполнителя). Email и пароли через эту таблицу недоступны.
11. **Для исполнителя чужая задача «не найдена»**, а не «доступ запрещён»: так не раскрывается, что она вообще существует.
12. **Роль хранится в таблице профилей, а не в данных аккаунта**, потому что данные аккаунта пользователь мог бы изменить сам. Профили создаются вместе с тестовыми пользователями (в сид-скрипте). Пользователь без профиля в систему не попадёт.

**Удаление**

13. **Объект, у которого есть задачи, удалить нельзя.** Сначала нужно удалить или перенести задачи (переноса в интерфейсе нет, см. ниже).
14. **При удалении задачи удаляется и её история.** Это единственный способ стереть историю, и доступен он только постановщику. Изменить или удалить отдельную запись истории нельзя никому.

**Техническое**

15. **Правила переходов лежат в таблице базы**, а не в коде. Интерфейс читает их оттуда же и показывает только доступные кнопки. Настоящую проверку делает база.
16. **Две одновременные смены статуса не пройдут обе:** задача блокируется на время операции.
17. **Правила работают для всех способов доступа**, включая прямые запросы к API в обход интерфейса.
18. **Интерфейс без UI-библиотеки**, простой CSS: дизайн по ТЗ не оценивается.

## Что не успел или упростил

- **Нет автоматических тестов.** Права и переходы нужно проверять вручную запросами к API.
- **Нет пагинации, фильтров и поиска** в списках.
- **Нет уведомлений и автообновления.** Страница обновляется после своих действий, чужие изменения видны после перезагрузки.
- **Нельзя перенести задачу на другой объект.**
- **Нет управления пользователями в интерфейсе.** Пользователей создают вручную в Supabase. Нет смены и восстановления пароля.
- **Запросы к базе делаются прямо в компонентах**, без отдельного слоя API и кэша. Для проекта такого размера это нормально, при росте запросы стоит вынести.
- **Мобильная версия базовая:** интерфейс не ломается на узком экране, но отдельно не дорабатывался.
- **Не проверялась работа на больших объёмах данных.** Индексы по исполнителю и объекту есть, но производительность правил доступа я не замерял.
- **Защита от подбора пароля** – только встроенная в Supabase.
